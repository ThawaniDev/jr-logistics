**Provider rule (the heart of "can be established without them")**: a provider is *available* only when its switch in the platform settings is ON **and** its credentials are complete (`…State() === "ready"`). Anything else is not an error: the feature is hidden/refused politely and the status page says why. In **demo mode** (`env.demoMode`) with nothing real configured the existing demo providers still work (the whole test suite relies on that); a real, ready provider wins over the demo one. `setSmsProvider(p)` / `setPaymentProvider(p)` stay as test overrides and win over everything.

**Effective delivery code**: the per-warehouse switch `requireDeliveryOtp` is honoured **only while an SMS provider is active** (real or demo). With SMS off, the recipient code is not demanded and no tracking/code text is sent (delivery proof = photo / signature as configured). The status page and the SMS settings tab say so in plain words.

### 9.2 What happens while each provider is off

| Provider | Off = switch off, or on without complete credentials | Effect |
|---|---|---|
| **SMS (Msegat)** | `smsEnabled` false, or no user name / sender / key (and not demo mode) | Nothing is texted (tracking link, delivery code, welcome message of a staff-created account); each skipped text is a `skipped` message-log row. **The recipient's delivery code is not demanded** (`requireDeliveryOtp` does not count): the driver scans the parcel code (+ signature where the warehouse asks). Immediate, also for parcels already on the road. Sign-in is unaffected (username + password). A gateway that is on but failing does **not** bypass the code. The status page and the SMS tab say so in plain words. |
| **Card (PayTabs)** | `paytabsEnabled` false, or no profile id / server key | The card option is hidden on the wallet; `POST /wallet/topup/card` answers `403 FEATURE_DISABLED` (off) or `503 DEPENDENCY_UNAVAILABLE` (not configured). Attempts already made keep being checked while credentials exist (a customer may have paid before the switch was turned off). |
| **Bank transfer** | `bankTransferEnabled` false, or bank / holder / IBAN missing | The bank option is hidden; the request route answers the same two codes. Requests already sent stay in Finance's queue and can still be decided. |
| **Both money methods off** | the default | The wallet says funding is arranged through support and shows the company contact; `POST /wallet/topup` answers `DEPENDENCY_UNAVAILABLE` in production; in demo mode the simulated top-up still works until a real method is ready; staff can credit by a wallet adjustment. |
| **Cash-risk limits** | `cashLimitsEnabled` false (or a figure at `0`) | No cash state, no block, no lien; the driver still sees his cash figure. |

### 9.4 Migration caveat (databases that ran the placeholders)

Drizzle's migrator applies only migrations whose journal timestamp (`when`) is **later than the last one recorded** in `drizzle.__drizzle_migrations`; it never goes back for an older one. During this round the slots **0029–0035 were placeholders** (`select 1;`, each with its journal entry already in place) while the workers wrote their real SQL. A database that ran `npm run db:migrate` (or started the app, which migrates) **in that window recorded those slots as applied**, so the real SQL written afterwards is **skipped** — the tables (`payment_intents`, `bank_transfers`, `legal_documents`, `privacy_requests`, `cash_risk_notices`, `document_expiry_notices`, `broadcasts`), the trigger `users_anonymised_guard`, the data clean-up of `0033` and the indexes are missing, and the first request that touches them fails with `relation … does not exist`. The system-status page **does not detect it** (it compares the number of applied migrations with the journal). `0036_app_errors` is unaffected on such a database (its timestamp is later and Drizzle will apply it) — unless it was applied before the earlier ones were.

**Fix (safe to repeat — every file is hand-written and idempotent: `IF NOT EXISTS`, `DO $$ … EXCEPTION`)**, from `web/`, on the affected database (the development database; the test database `jr_logistics_test` if it was migrated in the same window; **take a `pg_dump` first**):

```bash
for f in drizzle/0029_payments.sql drizzle/0030_legal.sql drizzle/0031_privacy.sql drizzle/0032_cash_risk.sql drizzle/0033_gaps.sql drizzle/0034_ops_tools.sql drizzle/0036_app_errors.sql; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f "$f" || break
done
```

(`0035_providers.sql` is `select 1;` — nothing to run. The `--> statement-breakpoint` markers are SQL comments; `SET LOCAL lock_timeout` needs the single transaction, which the flag provides.) Then run the `to_regclass` check of 9.3 and, from the test database, `tests/integration/data-schema.test.ts` (schema ↔ database parity). **Fresh databases and production** (still at 0028 or earlier) are unaffected: all pending migrations run in order in one transaction at container start, and nothing is skipped. If another worker's placeholder is replaced later, the same rule applies to the slot that changed: re-run its file by hand on every database that already recorded it.
