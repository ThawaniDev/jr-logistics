## Summary

The app is in good shape: every network call is single-flight, every stop action re-reads the job to settle an ambiguous failure (`runStopAction`/`_alreadyApplied`), models read the JSON defensively, i18n parity is perfect (10 413 keys, identical in en/ar/ur, placeholders consistent, every literal key used in Dart exists, no hard-coded English), all times go through one Riyadh formatter, the J changes (username login errors, routing OFF contract, office-driver wallet, J5 stat cards) work against the real server. No critical finding. The real problems are **truncated long lists without pagination**, **chat scroll jumping**, a few **non-idempotent writes with no "did it go through?" check**, a **crash on a 20-digit withdrawal amount**, **sign-out leaving the driver online**, and some store-readiness / platform items.

Counts: critical 0 · high 0 · medium 6 (all fixed) · low 17 (12 fixed, 1 partly fixed, 4 open: 14 info, 15 store checklist, 18, 21) · owner decisions 7 (answered by the lead: D1 keep, D2 yes, D3 keep, D4/D5/D7 owner items, D6 keep).

### Repeat-write probe — live result (private test database, server on :3107, `audit_a6_live_test.dart`, 9/9 green)

What the server answers when the same write is repeated after a lost answer (the app never retries writes by itself):

| write (app call) | repeated | what the app does |
|---|---|---|
| `accept` | `409 INVALID_TRANSITION` | **was** a confusing error toast; now "could not confirm" + lists refreshed (fix 5) |
| `checkin` | `409 INVALID_TRANSITION` | `_run(verify: status != accepted)` settles it |
| `loading-ack` | `200` (idempotent) | fine |
| stop `arrive` | `200` (idempotent) | fine |
| stop `deliver` (same code + OTP) | `200` (idempotent) | `runStopAction(verify)` — fine |
| stop `fail` (same reason) | `200` (idempotent) | fine |
| `deliver` after `fail` of the same stop | `409 INVALID_TRANSITION` | fine (the screen shows the real state) |
| `defer` | first call needs evidence (`422 EVIDENCE_REQUIRED`) — not exercised | `verify` on `deferCount` |
| `resend-code` | `200` (one more of the 3 resends) | cool-down + single flight |
| finish route (`delivered`) | `409 INVALID_TRANSITION` | `verify: !can(report_delivered)` — fine |
| `POST /withdrawals` | a second withdrawal (not idempotent by design; the first call could not run here: fresh driver has no balance) | `um.withdraw_unconfirmed` + list refresh — adequate |
| `POST /tickets` | **`200`/created again — duplicate ticket** | **was** a plain network toast; now "could not confirm" + list refresh (fix 5) |
| chat message, document upload, register | no server dedupe (code: messages/documents tables; register → `409 username`) | same treatment (fix 5, 13) |

## Checked and fine
