# Audit A3 — Order, job and field-ops lifecycle (2026-11-21)

Scope: `server/jobs.ts`, `stops.ts`, `requests.ts`, `shipments.ts`, `loading.ts`, `matching.ts`, `maintenance.ts` / `scheduler.ts` / `routes/cron.ts`, `notify.ts`, `route-plan.ts`, `routing-mode.ts`, `warehouse.ts`, `cod.ts`, `demo-shipments.ts`, partner sync (`partners/inbound|sync|outbox|poll`), plus the Riyadh-vs-UTC sweep and the routing × B2B mode matrix.
Method: read every state transition, then proved suspicions with DB-backed tests driven through the real API (`tests/integration/lifecycle-*.test.ts`, `field-mode-matrix.test.ts`; shared builder `tests/helpers/lifecycle-world.ts`). Run through `scripts/with-test-db.sh`.

## Summary

* The core machine is sound where it was already tested: exactly-one-winner slot filling, replay-safe stop actions, escrow conservation, lock order request → offer, per-parcel allocation, all-or-nothing, COD never touching the ledger, routing/B2B switches enforced on the server.
* **15 findings were confirmed and fixed (3 high, 9 medium, 3 low), each with a regression test**; 6 product decisions and 9 low open items are listed. Nothing speculative is reported: every row says how it was verified ("failed before" = the new test failed against the unfixed code in my first run; "code + test" = proved by code argument and a regression test that passes after the fix).
* The three most important: a **driver could re-answer the loaded count after the route started** (opened a bogus dispute and removed his own actions from the job screen); **one bad row aborted the whole housekeeping tick** (no expiry, refunds or auto-settlement until someone repaired the row; same for `POST /cron/tick` when any step threw); **ops cancelling a request mid-route silently dropped the stops a driver had already delivered** (driver unpaid, business refunded for delivered parcels).
* Riyadh-vs-UTC: no business-day logic in the lifecycle code was wrong except document expiry ("expires ON a date" was UTC: valid 3 h too long) — fixed; the rest of the sweep (table below) is clean or belongs to A4.
* Routing × B2B × office/direct driver (8 combinations): a whole job + 40 business/office/admin/driver views each, no 5xx, flags consistent, `routeApprovedAt` set in both modes.

## Needs owner decision

1. **Cancel mid-route (finding 3)** — default implemented: refuse and point to "end route". Alternative: let cancel settle the delivered stops automatically (needs a money rule).
2. **No-show can be recorded at T+0** (`confirmAttendance` only requires `startsAt <= now`); the 30-min `lateGraceMin` only drives the ops alert. A driver 5 minutes late can be removed and replaced. Recommended default: business needs `now >= startsAt + lateGraceMin`, staff exempt.
3. **A lapsed offer cannot be re-taken**: an `expired` offer row blocks both re-offer (unique) and `apply` (`CONFLICT`) and hides the request from the driver's opportunities. A driver who missed a push for 2 h can never take a still-open request. Recommended: allow `apply` on own `expired` offer (refresh the office snapshot).
4. **Routing OFF shows every recipient's name + phone from the moment a job is accepted** (J2 as decided; routing ON reveals only the current stop). A driver who accepts and cancels keeps up to 30 recipients' phones. Recommended: reveal name/phone from the moment the parcel is scanned onto the vehicle (`status = loaded`).
5. **Portal `POST /requests` has no idempotency key** (the public API has): a retry after a lost answer duplicates an order and reserves its escrow twice. Recommended: accept `Idempotency-Key` on the portal route through `api_idempotency` (A5 should also disable the button while in flight).
6. **All-or-nothing call-off** (`maintenance`) cancels every offer incl. one that already delivered parcels before the start time (rare: needs a check-in 3 h early and deliveries before start). Same rule as finding 3 would apply.

## Open (not fixed, low)

1. **Replays of `accept` / `reject` / `checkin` / `delivered` / `cancel` answer `409 INVALID_TRANSITION`** after a lost response (stop actions are idempotent, these are not). The app handles it with re-fetch (A6); API clients must too. Recommended: replay of the *same* terminal action by the same driver → 200 with the offer.
2. `POST /cron/tick` does not take the scheduler's advisory lock: an external cron plus `INTERNAL_SCHEDULER=true` can run two ticks at once. Maintenance is idempotent (row locks + re-checks) but `remindIncompleteParcels` can then notify twice.
3. `reportNoWork` is accepted after the driver has already delivered stops (the API allows what `driverActions` does not offer); it only opens an urgent ticket.
4. `ensurePickupPin` may call Google Geocoding (≤ 8 s) inside the publish transaction while holding the request lock — bounded, only when no pin exists.
5. `officeWindowMin` / `officeWindowEndsAt` branch in `runMaintenance` is dead since C9 (column is always null) — harmless query each tick.
6. `opsAlerts` still builds `settlement_pending`, `delivery_unconfirmed`, `qty_dispute` alerts for states that E16/E18 removed (always empty).
7. `updateSettings` is a read-merge-write without a lock (two admins saving different fields at the same instant: last writer wins the whole object); the 5 s settings cache is per process, so after toggling routing/B2B another instance follows within 5 s.
8. Two stops arrived at / delivered at the same instant (routing OFF) can both trigger `sendRecipientCodes` before `notifiedAt` is written → the recipient may get the same SMS twice (same code).
9. `unlinkDriver` / `respondInvite` check "active job" outside the offer lock; a driver accepting at the same instant keeps the old office snapshot on that offer.

## Checked and fine

* Slot filling: `lockOffer` locks request → offer; N drivers racing for N slots (existing test + races suite); `fillSlot` re-checks request status and slot count after the lock.
* Stop actions: replay semantics (same code / same fail reason), wrong-code counter committed before the rejection, `OTP_LOCKED` after 5 even under 8 parallel guesses (races suite), COD exact-amount rule, signature/evidence consumption (media bound to the stop, kind and uploader, single use).
* Finish-route ×2, end-route vs finish vs ops end-route, deliver vs fail, cancel ×3, publish ×3, cancel-parcel ×3, COD receive ×3, three maintenance ticks at once: one outcome each, money invariants hold (`moneyViolations()` empty).
* Geofence: GPS required with a known pin, radius from settings, unknown pin recorded as `arrival_unverified`, business-confirmed attendance bypass is deliberate (business owns the pin).
* Routing OFF: no Google call from planning, `routeApprovedAt` set by loading confirmation / first stop action / approve no-op, mid-flow jobs keep working after a switch flip, switch ON again never clears `routeApprovedAt`.
* B2B OFF: refused on every manifest entry point, coerced for API / re-ship / demo parcels; existing business parcels keep working (matrix).
* Partner sync: events de-duplicated by (order, status, second) + same-change window, effects applied before the seen-marker, future timestamps clamped, outbox claim = compare-and-set with 5-min lease, per-connection fairness + circuit breaker, journey hook in a savepoint (never blocks a delivery), no echo of partner-originated cancels, secrets never in notifications.
* Notifications: payloads carry refs / codes / counts only (no phone, address, IBAN, OTP); text is resolved per viewer language client-side; office drivers get earning-free offers; ops fan-out limited to active admins + staff holding the permission.
* Public tracking: code + last 4 digits, generic 404, per-IP and per-code limits.
* Demo parcels: 404 outside demo mode, deterministic, consumer-only while B2B is off.
