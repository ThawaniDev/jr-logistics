# Audit K — A4 Data layer, performance and reports (2026-11-21)

Scope: `db/schema.ts`, `drizzle/*`, `server/analytics/*`, `server/export/*`, `scripts/*` (+ the capture / retention code of `server/snapshots.ts` and the demo-history runner). Databases used: the dev DB `jr_logistics` (read-only for data; migrations 0023–0028 applied), a **scratch** database `jr_scale_test` (365 days · 100 companies · 10 offices · 300 drivers = 150 000 parcels, 115 000 offers, 24 000 requests, 22 600 settlements, 1.19 M parcel events, 0.88 M job events, 344 000 notifications, 1.6 GB, i.e. 7–11× the dev DB — created by the seeder and dropped by me), a `pg_dump` **copy of the dev DB** (used to rehearse the migrations, the backup and the 1.2 M-row availability experiment, dropped) and a private test database. Timings were taken on a machine whose load average was 8–35 (other audit workers): they are upper bounds, buffer counts are exact.

## Summary

* **Verdict.** The data layer is in good shape: every report ties to independent SQL (checked below), no report is slow at 7–11× the demo volume (all 11 reports ≤ 0.6 s for 30 days, ≤ 1.4 s for 12 months; every drill-down table page ≤ 0.25 s; no timeouts), the schema has real integrity checks, and all 29 migrations apply to an empty database and to a copy of the dev DB in about a second each. What was wrong sits at the edges: three **growth-bound** query shapes, one **latent overflow** that would have stopped every payout, a **formula-injection** gap in the CSV writer, **unsafe parallel migration** at container start, and **unbounded growth / privacy** of two capture tables.
* **Counts.** 21 findings: 1 high (latent), 9 medium, 11 low / info — 16 fixed (or given a tool), 5 open (4 need an owner decision or another owner's file), plus 5 cross-area hand-offs. **Tests added: 27** (unit 12, integration 15) in 7 new files, plus 2 adjusted; the guard tests were checked red on the unfixed code (mutation) — see "Tests".
* **Migrations added (I own them): `0023_data_audit`, `0024_wallet_bigint_ledger_guard`, `0025_offers_driver_accepted_index`, `0026_payout_batch_total_bigint`, `0027_drop_email_lower_check`, `0028_notifications_created_index`.** Applied to the dev DB and the shared test DB. Nothing in them rewrites a large table or holds a lock for longer than a catalogue change (details below).

## Schema and constraint review

53 tables · 93 FKs · 32 CHECKs (29 `NOT VALID`) · 241 indexes (84 unique) after this audit.

* **Status enums.** CHECKs exist for users (role, status), requests (status, service), offers, shipments (status, recipient_type), settlements, withdrawals, tickets, complaints, documents, webhook deliveries, partner outbox / connections. **No CHECK** (text enums the code writes from several places, so adding one blind could reject a legitimate value): `driver_profiles.verification_status / availability / office_link_status`, `business_profiles` / `office_profiles.verification_status`, `pricing_rules.status / unit`, `office_invites.status`, `office_agreements.status`, `custody_items.status`, `partner_orders.state`, `ledger_entries.kind` (the schema comment missed `charge`; fixed), `requests.created_via`, `shipment_media.kind`, `message_log.channel / status`, `login_events.method`. Violations today: 0 for every one of them (SQL). Recommendation: add them `NOT VALID` once each write path is listed — not done, no confirmed bug.
* **Non-negative money / arithmetic.** Existing: `wallet_nonneg`, `pricing_positive`, `withdrawal_pos`, `cod_remittances_positive`, `settlements_money_chk`, `offers_units_chk`, `requests_money_chk`. Added (0023, each only if existing rows comply): invoices add up and are ≥ 0, settlement VAT / refund ≥ 0, parcel COD ≥ 0, request totals ≥ 0, wallet kind ↔ owner, lower-case username, one platform wallet. Per-row amounts stay `integer` (bounded by the API: price ≤ SAR 1 M, 500 vehicles × 90 days; an overflow is a 422, never a wrong number); the one accumulator that could overflow, the wallet balances (+ `payout_batches.total_cents`), is `bigint`.
* **Foreign keys / `onDelete`.** 93 FKs. Users are never deleted (no NO ACTION problem); `requests → offers / shipments / job_events / messages / shipment_events` cascade, but `settlements`, `ledger_entries`, `ratings`, `cod_remittances`, `invoices` reference offers / requests with NO ACTION, so **a request with money history can never be deleted** (protective; only drafts are). Sessions, profiles, notifications, location history cascade from the user; `login_events.user_id` is SET NULL. uuid columns without FK are log / audit / outbox references by design (`audit_logs.actor_id`, `message_log.*`, `partner_*`, `webhook_deliveries.request_id`, `shipment_events.actor_id` …) plus two dead ones: `settlements.batch_id` (payout batches retired by E18) and `offers.replaces_offer_id`. Orphan scan on dev: 0 for every non-FK reference that has a target table.
* **Unique indexes.** Present for every natural key (`ref`s, `code`, `number`, `idempotency_key`, `settlements.offer_id`, `invoices.settlement_id` partial — A2 asked, it exists since 0007, created inside a guard that silently skips on duplicates: verify on production —, one pending invite / accepted agreement per office, one rating per offer and rater). Added: one platform wallet. Not unique by design: `terms_consents` (an immutable acceptance log), `api_keys.prefix`.
* **Nullable columns.** `users.username` stays nullable (a few internal tools insert users without one; sign-in falls back to e-mail); nothing found that should be `NOT NULL`.
* **Redundant / unused indexes.** 6 dropped (above). Never-scanned on the dev DB (app + tests + e2e): `message_log_ref_idx`, `dlh_offer_idx`, the shipment search indexes (`shipments_ref_lower_idx`, `_name_lower_idx`, `_phone_last4_idx`, `_address_city_idx`) — feature indexes, kept; on the report-only scratch workload `shipment_events_actor_idx` 54 MB, `events_actor_idx` 41 MB, `shipment_events_offer_idx` 38 MB were unused (they serve the per-actor / per-offer activity pages): **check `pg_stat_user_indexes` on production before dropping any**.
* **`schema.ts` ↔ database.** Everything `schema.ts` declares (indexes, CHECKs) exists in the migrated database (test). The reverse does not hold (item 17).

## Migration safety review (what a deploy against a big production DB would lock)

The migrator (`drizzle`) runs **all pending migrations in one transaction** and cannot run `CREATE INDEX CONCURRENTLY`; there are no down migrations (forward-only; roll back with a restore); the container migrates on every start (now serialised, finding 5).

| migration | what it does | lock / cost on a big table |
|---|---|---|
| 0000–0004, 0006, 0008–0013, 0016, 0022 | create tables; `ADD COLUMN` nullable or with a **constant** default; indexes on new (empty) tables | metadata only (PG ≥ 11); safe |
| 0007 | 27 `CREATE INDEX` on `ledger_entries`, `settlements`, `job_events`, `requests`, `shipments`, `tickets` … | **blocks writes** on each table for the build (seconds per million rows; `shipments` gets 5); CHECK / FK are `NOT VALID` (brief lock) |
| 0013 (partner sync) | `partner_outbox ADD COLUMN seq bigserial NOT NULL` (volatile default → table rewrite, ACCESS EXCLUSIVE), `SET NOT NULL` | small table; fine |
| 0014, 0017, 0018, 0019, 0020 | ~45 more non-concurrent indexes (`shipments` +10, `requests`, `offers`, `settlements`, `ledger_entries`) | the big one: writes to `shipments` wait for each build. On a table of millions of rows create the index by hand first with `CONCURRENTLY IF NOT EXISTS`; the migration is then a no-op |
| 0012 | UPDATE / INSERT backfills over `sessions`, `offers`, `job_events`, `shipments` in the migration transaction | row locks for the duration; one-time |
| 0021 | per-user loop (O(n²), item 18) then `ADD CONSTRAINT UNIQUE` | ACCESS EXCLUSIVE on `users` while the index builds |
| **0023** | `DROP INDEX` ×6, one partial unique index on `wallet_accounts`, 6 guarded `CHECK … NOT VALID` (an `EXISTS` read of the table first), `SET LOCAL lock_timeout '10s'` | metadata + one read per table; seconds on the dev data, a sequential read of `shipments` / `settlements` / `invoices` / `requests` / `users` / `wallet_accounts` on a big database |
| **0024** | `wallet_accounts` ×3 columns `int → bigint` (table rewrite, ACCESS EXCLUSIVE — one row per user: 100 000 users ≈ 1 s, rebuilds 2 indexes), a trigger on `ledger_entries` (row events only) | seconds; `lock_timeout` fails fast behind a long transaction |
| **0025** | `CREATE INDEX` (partial) on `offers` | SHARE lock for the build; create it `CONCURRENTLY` first on a big table (the file says how) |
| **0026** | `payout_batches.total_cents → bigint` | retired, tiny table |
| **0027** | drops `users_email_lower_chk` on databases that ran the first 0023 | metadata only |
| **0028** | `CREATE INDEX` on `notifications(created_at)` | SHARE lock for the build; create it `CONCURRENTLY` first on a big table (the file says how) |

Rehearsed: the full chain on an empty database (3 parallel migrators), and 0023–0026 on a `pg_dump` copy of the dev DB (≈ 1 s each); every `NOT VALID` constraint (old and new) validates on the copy. **Backup / restore** (A7 owns the RUNBOOK; my rehearsal): `pg_dump -Fc` of the dev DB 1.5 s / 13 MB, `pg_restore --no-owner` into an empty DB 6 s, identical row counts on 9 tables and 23 migration rows.

**Growth plan (nothing to do before ~2 M parcels in a reported window).** (1) `PARCEL_OUTCOME_AT` is a CASE over `delivered_at / failed_at / returned_at / updated_at`: an expression index would help but referencing `updated_at` makes every `shipments` UPDATE non-HOT (22 indexes to maintain), so the clean fix is a stored `outcome_at` column set where the outcome is written (A3's write paths) — then index it. (2) Reports whose OR-window spans two tables (`offers.created_at / accepted_at` OR `requests.starts_at`) read the whole join: rewrite as a `UNION` of three index-friendly selects. * **Riyadh day bucketing.** `bucketSql` and `windowOf` are exact: a Riyadh day is `[21:00Z, 21:00Z)`; `today` at 20:59Z is the 20th, at 21:30Z the 21st; weeks start on Sunday; leap day, month ends (`mtd` on 31 Mar vs February, `qtd`, `ytd` on 29 Feb 2028, `12m`) all give the documented comparison windows. **Time-zone independence:** all 11 reports + 58 tables + results dumped under `PGOPTIONS="-c TimeZone=UTC"` and under Asia/Riyadh: the only differences are the "age since now()" values. The one place that used the session day was the Explorer (finding 3); a static test now forbids it in `server/analytics` and `server/export`. The sweep for `current_date` / `current_timestamp` / `now()::date` / `date_trunc('day'` / `::date` found nothing else: every remaining `date_trunc` and `::date` carries `at time zone 'Asia/Riyadh'` or is an hour truncation / cast of a text literal (Riyadh is a whole-hour offset); the JS side does its Riyadh day arithmetic on fixed +3 h in `analytics/time.ts`.
