## J1 — Username + password login (worker A, MA)

* **Username**: `users.username text unique` (lower-case; 3–30 chars; `[a-z0-9._-]`, starts with a letter or digit; reserved words refused). Case-insensitive matching (always lower-case before compare/store). Migration 0021 adds the column + unique index and backfills: staff/admin → `lower(split_part(email,'@',1))` (suffix `-2`, `-3` … on clash); everyone else → `'u' || digits of phone` (e.g. `u966500000001`); then a script `web/scripts/backfill-auth.ts` (`npm run db:backfill:auth`) sets a password for **demo accounts only** (`is_demo = true` → `Demo#Pass2026`, `must_change_password = false`) and gives demo accounts readable usernames (`demo.business`, `demo.driver`, `demo.office`, …; read `scripts/seed.ts` for the list). Real (non-demo) accounts without a password cannot sign in until staff set one (J1d).
* **Login** `POST /auth/login` `{ username, password }` (public; `username` may also be an e-mail address — matched against `users.email` when it contains `@`). Same hardening as today's staff login (rate limit per ip+identifier 10 / 15 min, generic `401 UNAUTHENTICATED "Invalid credentials"`, constant-time dummy compare, lockout after 5 wrong passwords for 15 min, suspended account refused, login events recorded with `method: "password"`). Response `{ token, user }`, or `{ mfaRequired: true, mfaToken }` for staff/admin with two-step verification on (second step stays `POST /auth/staff/login/mfa`; the session cookie is set for `client = web`). Works for **every role** (business, driver, office, staff, admin). `POST /auth/staff/login` stays as an alias (accepts `{ username?, email?, password }`) so nothing else breaks. `users.must_change_password` → after login the clients send the user to a "choose a new password" screen (web `/staff/change-password` generalised to `/account/change-password`, mobile equivalent).
* **Register** `POST /auth/register` (public, 201): `{ role: business|driver|office, username, password, name, phone, email?, city?, language?, companyName?, … same profile fields as today …, termsAccepted }` → `{ token, user }`. **No OTP any more** (the phone is a contact number; accounts are verified by staff through documents, as before). `409 CONFLICT` with `details.field` = `username` | `phone` | `email`. * `POST /auth/change-password` now for **all roles** (it is already implemented for staff; open it to everyone; revokes the other sessions). A profile "Change password" card on every portal (business, driver, office profile pages) and in the mobile profile screen; the profile page also shows (and, for self-registered users, lets them change) the username? — **no**: the username is changed only by staff (J1d).

The "people sign in by OTP" copy anywhere in the UI/docs/notes is replaced.

Keep `sendSms()`/the SMS provider boundary (recipient delivery codes use it) and keep the `otp_codes` table (no destructive migration). * **When routing is OFF** (everything below is enforced on the server, then hidden in the clients):
  1. no route planning call to Google at all (publish-time planning, hand-over planning, `POST /offers/:id/route/optimize` → `409 ROUTING_DISABLED`, `route`/`legPolyline` data not produced; `route` in the job view = `null`);

  3. **no one-stop-at-a-time lock**: any `loaded` stop of the driver's own job can be arrived at / delivered / failed / postponed in any order (`STOP_LOCKED` is not raised); "current stop" is just the first unresolved one in manifest order; manual reorder is off;
  4. the driver sees **name, phone and address of every stop of his own job** (`driverStopView` sets `recipientName`/`recipientPhone` for all non-resolved own stops) and may open WhatsApp for any of them (`GET /driver/jobs/:id/whatsapp?shipmentId=` allowed for any own stop of an active job);
  5. map/route UI (route map panel, reorder, "optimise", polyline) is hidden on web and mobile; the geofence/arrival/loading/COD/OTP rules are unchanged.
* **When routing is ON**: behaviour exactly as today.

* **As built (F1, server)** — contract for web (F2) and Flutter (MJ):
  * Setting `routingEnabled` (default `false`) in `GET/PATCH /admin/settings` (boolean, `settings.edit`, audited old → new like every setting). `GET /catalog` → `policy.routingEnabled`, `policy.b2bShipmentsEnabled`; `policy.driverCanReorderRoute` there is now the **effective** value (`routingEnabled && driverCanReorderRoute`).

Routing OFF: `route` is `null`; `actions` never contains `approve_route` (loading confirmed → `["work_stops","end_route"]`, or `["report_delivered"]` when nothing is left); `routeApprovedAt` is non-null from the moment loading is confirmed (see below).

Routing OFF: `recipientName` + `recipientPhone` for every stop of the driver's own job that is not resolved (also while still scanning; resolved stops keep the name, never the phone); `current` = first unresolved stop in manifest order (only once loading is confirmed); `canDefer` and the door timer (`waitRemainingSec`) belong to **every** open stop, not only the current one. Routing ON: exactly as before.
  * Routing OFF, errors/behaviour: `POST /offers/:id/route/optimize`, `POST /offers/:id/route/reorder` and `GET /driver/jobs/:id/route-geometry` → `409 ROUTING_DISABLED` (checked before ownership); `POST /offers/:id/route/approve` is a harmless idempotent no-op (200, returns the offer; before loading is confirmed `409 INVALID_TRANSITION`); no `STOP_LOCKED` (arrive / deliver / fail / defer / media / resend-code on any own `loaded` stop; arrival, parcel code, OTP, COD and signature rules unchanged; replays idempotent); `GET /driver/jobs/:id/whatsapp?shipmentId=` works for any stop of the driver's own active job (another job's parcel → 404); no Google Routes/Geocoding call from planning (`autoPlanRoute` is a silent no-op).
