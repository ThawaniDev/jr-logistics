# Shipping Partner
 Shipping Partner Integration API 
 Introduction 
 The Shipping Integration API is Omniful's standardized contract for connecting third-party shipping integrators to the Omniful platform. Instead of building a bespoke integration for every carrier, Omniful defines one consistent JSON contract — you implement it once on your own server (your base_url ), and Omniful handles the rest. 
 At a high level: 
 
 You (the integrator) expose a set of REST endpoints — create/cancel shipment, track, get AWB label, register webhook, etc. — that follow Omniful's request/response shapes. 
 
 Omniful calls these endpoints whenever a merchant creates, cancels, or tracks a shipment through your carrier, and optionally receives status webhooks from you in return. 
 
 Every response follows a single success/error envelope , so parsing logic stays uniform across all integrators. 
 
 Authentication is pluggable — either a static API key or an OAuth-style access token with a refresh flow — configured once during onboarding. 
 
 
 For common implementation questions, see the FAQs section below. 
 

 

 

 Reference 
 Request timeout 
 Omniful applies a 10-second timeout to every request sent to your base_url . A response outside this window is treated as a failed request on Omniful's side. 
 Ensure your integration responds well within this limit, especially for synchronous operations like Create Shipment . 
 
 AWB label rules 
 
 
 
 Rule 
 Detail 
 
 
 
 
 Format 
 awb_label must be a publicly accessible, working URL ( http:// or https:// ) pointing directly to a PDF label file 
 
 
 Content-Type 
 The URL must return the file with Content-Type: application/pdf 
 
 
 Recommendation 
 It is recommended to send the label URL with a .pdf extension 
 
 
 Not supported 
 Base64-encoded data, raw binary, or any non-URL format 
 
 
 Access 
 The URL must resolve without authentication and remain valid 
 
 
 Failure handling 
 If Omniful cannot download the file from your URL, the shipment is still surfaced as created, but without a usable label . The merchant can retry via Get AWB Label (or Get Return AWB Label for returns) once the URL is reachable 
 
 
 
 
 Custom fields ( meta.custom_fields ) 
 Custom fields are configured by Omniful's internal team via the partner onboarding dashboard when your app is published — not set directly through the API. When submitting your integration, you provide your base_url , logo, supported endpoints, and the custom field definitions below. 
 Field definition attributes 
 
 
 
 Attribute 
 Description 
 
 
 
 
 Label 
 Human-readable name shown to the merchant (e.g. "Service Type") 
 
 
 Key 
 Stable key sent in the custom_fields array's key attribute (e.g. service_type ) — this is what your integration matches against 
 
 
 Description 
 Optional help text shown to the merchant 
 
 
 Type 
 Text (free input) or Dropdown (fixed set of options) — these are the only two supported types 
 
 
 
 For Dropdown type fields, each option has its own Label (shown to the merchant) and Key (the value actually sent to your API). 
 Example 
 A Dropdown field labeled "Service Type" (key service_type ) can have options like: 
 
 Express Delivery -> express 
 
 Next Day Delivery -> next_day 
 
 
 If the merchant selects Express Delivery , your integration receives: 
 { "key": "service_type", "value": "express" }

 
 
 Note: you always receive the option's Key , never the display Label. 
 
 Custom field definitions are configured once per partner account — they are fixed at onboarding/publishing time and do not vary per shipment. Every shipment for that partner sends the same set of custom_fields keys (values resolved per shipment, but the field definitions themselves are static). 
 Per-shipment values : Custom field values can be resolved on a per-shipment basis using Omniful's automation rules. Omniful clients can configure shipping automation rules to automatically set the appropriate custom field values for each shipment based on their business requirements 
 
 Base URL & path construction 
 Omniful constructs the full request URL by concatenating your base_url with the fixed path suffix for each endpoint. You do not need to include endpoint-specific path segments in base_url — just the scheme + host (and a custom prefix, if you have one). 
 full_url = base_url + endpoint_path

 Examples 
 
 
 
 Your base_url 
 Endpoint path 
 Full URL called 
 
 
 
 
 https://partner.example.com 
 /shipments 
 https://partner.example.com/shipments 
 
 
 https://partner.example.com/api 
 /shipments 
 https://partner.example.com/api/shipments 
 
 
 
 Notes 
 
 base_url may be provided with or without a trailing slash — Omniful normalizes the URL before concatenating the endpoint path, so https://partner.example.com/ and https://partner.example.com are treated identically. 
 
 A custom prefix (e.g. /api , /shipping ) is fine — it becomes part of base_url itself, not something Omniful appends separately. 
 
 There is no version prefix (e.g. no /v1 ) — paths are appended directly to your base_url . 
 
 
 
 Response envelope 
 Every endpoint returns the same wrapper shape. 
 Success 
 { "success": true, "data": { ... } }

 
 
 HTTP status 2xx 
 
 success must be true 
 
 data is required and must not be null 
 
 
 Error 
 {
 "success": false,
 "error": {
 "code": "VALIDATION_ERROR",
 "message": "Human readable error message"
 }
}

 
 
 HTTP status 4xx or 5xx 
 
 success must be false 
 
 error.code and error.message are required 
 
 If success is false or data is missing on a "successful" HTTP status, Omniful treats it as a failure and surfaces error.message (falling back to the raw response body if none is provided) 
 
 
 Suggested error.code values 
 You can use generic error codes like these as needed: 
 VALIDATION_ERROR , AUTHENTICATION_ERROR , NOT_FOUND , ALREADY_CANCELLED , INTERNAL_ERROR

 Frequently Asked Questions 
 Can shipping automation rules be configured for this flow, so orders can be assigned automatically to Shipping Partner based on our business rules? 
 Yes. Once this Custom App integration is configured and enabled in Omniful, it can participate in the same shipping allocation and automation flows used for other shipping partners, subject to your configured capabilities and business rules. 
 
 Will Shipping Partner appear in Omniful as a selectable shipping partner/carrier, similar to other integrated carriers? 
 Yes. After onboarding and configuration, the shipping partner appears in Omniful like other integrated carriers, and can be selected wherever that partner is enabled and applicable. 
 
 Will the AWB, tracking number, and shipping status updates be reflected back in Omniful? 
 Yes. Omniful stores the shipment AWB / tracking number returned by your create API, can fetch the AWB label from your label API, and updates shipment status from your tracking API and/or inbound webhooks. 
 
 What are the two supported authentication types, and how do they differ? 
 api_key is a static bearer token validated on every request — no refresh flow needed. 
 access_token is dynamic: Omniful calls your POST /auth/token endpoint with client_id , client_secret , and grant_type to obtain an access token, then sends it as a Bearer token on subsequent calls. Omniful automatically re-fetches the token when a request comes back 401 Unauthorized , and retries the original request with the refreshed token. 
 
 What happens on a 401 response? 
 For access_token integrators, a 401 triggers Omniful's built-in refresh flow: it calls your token endpoint again, stores the new token, and retries the failed request once with the new credentials. 
 For api_key integrators, there's no refresh — a 401 is treated as a genuine auth failure. 
 
 What does the response envelope look like, and is it consistent across all endpoints? 
 Yes — every endpoint returns the same wrapper shape: 
 Success: { "success": true, "data": { ... } } with HTTP 2xx and a required, non-null data . 
 Error: { "success": false, "error": { "code": "...", "message": "..." } } with HTTP 4xx/5xx. 
 If success is false or data is missing on a "successful" HTTP status, Omniful treats it as a failure and surfaces your error.message (falling back to the raw response body if none is provided). 
 
 What's the request timeout? 
 Omniful applies a 10-second timeout per request to your base_url . If your server doesn't respond within this window, Omniful treats it as a failed request. Ensure your integration responds well within this limit, especially for synchronous operations like Create Shipment. 
 
 How should I return AWB labels? 
 awb_label must be a publicly accessible, working URL ( http:// or https:// ) pointing to a PDF label file, . Raw label data — base64, embedded PDF bytes, or any non-URL format — is not supported . 
 See the AWB label rules section above. 
 
 How do custom fields ( meta.custom_fields ) work? 
 Custom fields are configured by Omniful's internal team when publishing your integration, not something you configure directly via API. When submitting your app for review, you provide your base_url , logo, supported endpoints, and the custom field definitions you need. 
 See the Custom fields section above. 
 
 How does Omniful validate my account/credential setup before activating an integration? 
 Through a health check: 
 
 For access_token integrators, this is the same token refresh flow ( POST /auth/token ). 
 
 For api_key integrators, Omniful calls POST /auth/validate with the merchant's API key. 
 
 
 Either way, Omniful confirms the credentials work before marking the account active. 
 
 Do I need to implement webhooks? 
 Webhooks are optional but recommended for real-time status updates. If supported, you register your webhook URL via Register Webhook , and Omniful expects you to POST shipment status changes to it as they happen, rather than relying solely on polling via the track endpoint. 
 
 What's required vs. optional in request/response payloads? 
 Fields are documented with explicit presence rules: 
 
 
 
 Label 
 Meaning 
 
 
 
 
 Required 
 Must be non-empty 
 
 
 Optional 
 May be omitted 
 
 
 
 Always check the field table for each endpoint rather than assuming based on naming. 
 
 Do I need to include a path in my base_url ? 
 No — just the scheme and host (plus any custom prefix like /api , if you have one). Omniful appends the fixed endpoint path to whatever you provide. 
 See the Base URL & path construction section above. 
 How does Omniful onboard a new Shipping Partner, and what details are required? 
 
 To onboard a new Shipping Partner, Omniful requires the following details: 
 
 Shipping Partner Name — The name that will be displayed in Omniful. 
 
 Logo — The Shipping Partner's logo to be displayed in the Omniful interface (10KB). 
 
 Supported Endpoints — The APIs/endpoints supported by the integration, such as Create Shipment, Cancel Shipment, Label, Tracking, Returns, etc. 
 
 Custom Fields — Any additional shipment-level fields required by the Shipping Partner. These are configured by Omniful's internal team as part of the integration setup. 
 
 
 Once these details are provided and the integration is reviewed and configured, Omniful publishes and enables the Custom App so it can be used like other supported Shipping Partners. For the complete onboarding requirements and process, see the Shipping Apps Onboarding Documentation .
